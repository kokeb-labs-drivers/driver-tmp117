Detailed Description

template<I2cPort Port>
class tmp117::TMP117< Port >

Driver for one TMP117 on a platform port.

Lifecycle: construct with the configuration (no I/O), then EnsureInitialized(), the one way to start (bus up, wait for the power-up load, identity, configuration, read-back), use, optionally Deinitialize() (shutdown). Every call that touches the chip returns Error::NotInitialized until EnsureInitialized() has succeeded, except Deinitialize() (row N1 of docs/contract.md: Ok and no I/O on a driver that never reached the chip, so a converting chip keeps converting); no call starts the chip as a side effect.

Port hooks:

Hook Used for Without it
void DelayUs(uint32_t us) noexcept Power-up load, conversions, EEPROM programming Compile error: the waits are required
bool ReadAlertPin(bool& level) noexcept The raw level of the ALERT pin, for ReadAlertPin() ReadAlertPin() returns Unsupported; poll ReadStatus() instead
void Log(LogLevel, const char* message) noexcept One line per lifecycle event or failure Nothing is logged

A hook declared with the wrong signature is a compile error.

◆ Deinitialize()

template<I2cPort Port>
Result< void > tmp117::TMP117< Port >::Deinitialize ( )
noexcept

Put the chip in shutdown, its low-power safe state, and mark the driver uninitialised.

Follows the switch-off decision table of docs/contract.md. An initialised driver sends one Configuration write with MOD = shutdown, whatever doubt it holds about the chip (never as the tail of another write). Does nothing, with no I/O, when the driver never reached the chip (also after a start-up refused for an argument or a port that did not come up). The driver is uninitialised afterwards even if the write failed. A driver that lost track of the chip reads EEPROM_UL first. While a clean reply shows EEPROM_Busy (the power-up load, or a word being programmed) it sends nothing: it waits 7 ms and reads again, at most twice per call. Then it writes the lock (EUN = 0, a write that programs no EEPROM) and reads it back, at most twice, and sends the shutdown write unless the read that follows the last lock write is clean and shows EUN = 1 (ambiguity A21). A failed or garbled read is no evidence and never refuses. After a Device_ID mismatch it reads Device_ID first and sends nothing to another device. At most 8 transfers (9 after a mismatch) and 14 ms of delay.

Returns
Ok, Bus (the shutdown write failed, or no answer to the read and the lock write), Timeout (EEPROM_Busy still set after two waits; nothing sent, call again), DeviceIdMismatch (another device answers; nothing sent) or EepromVerifyFailed (EUN reads 1 after the last lock write; nothing sent). Ok means the write was acknowledged; the residual risks of docs/contract.md still apply.

◆ EnsureInitialized()

template<I2cPort Port>
Result< void > tmp117::TMP117< Port >::EnsureInitialized ( )
noexcept

Start the chip, once: the only way to initialise the driver.

Brings the bus up, waits for the power-up load (section 7.5.1.1, p. 18: 1.5 ms typical, no maximum printed, so a bounded busy poll follows, Config::reset_timeout_ms), checks Device_ID, reads EEPROM_UL and locks the EEPROM first when EUN reads 1 (a write would otherwise be programmed as a power-on default, section 7.5.1.2, p. 18), writes the limits, the offset and the configuration and reads them back. After it succeeds, later calls return Ok at once with no I/O. After it fails, the driver stays uninitialised and the next call starts again from the beginning. It does not reset the chip: the chip is in the state its EEPROM gives it, and the configuration is written over it.

Returns
Ok, InvalidArgument (the address or the stored configuration is out of range; no I/O), Bus, Timeout (EEPROM_Busy never cleared), DeviceIdMismatch, BadReply (a reserved bit set, or a register that does not read back what was written) or EepromVerifyFailed (EUN is set and could not be cleared; nothing else was written).

The flags seen by any Configuration read since the last ClearLatchedStatus(), the driver's own reads included. No I/O.

Every read of Configuration the driver makes ORs the three clear-on-read bits into this latch, so no internal read hides an alert or a data-ready from the caller (handbook KB-CPP-119). In therm mode the alert flags are a level that follows the temperature (section 7.4.4.2, p. 17): the latch says "seen since the last clear"; ReadStatus() gives the present state.

Returns
The latched flags (eeprom_busy is never latched).

◆ ProgramPowerOnDefaults()

template<I2cPort Port>
Result< void > tmp117::TMP117< Port >::ProgramPowerOnDefaults ( const Config &  defaults)
noexcept

Program the power-on defaults (limits, offset, configuration) into EEPROM.

One guarded operation, never implicit (7.5.1.2, p. 18; endurance 1000 writes, section 6.6): shut the chip down, unlock, write each word (the Configuration word last: with a continuous MOD the chip converts from that write on, ambiguity A20), wait and poll EEPROM_Busy with a deadline, then lock again on every path: write EUN = 0 (ambiguity A6), reset (a soft reset; the general-call reset only with Config::allow_general_call, ambiguity A5), check that EUN reads 0, read the words back and compare, then start the running configuration again. EEPROM1 and EEPROM3 are never written. Nothing else may use the bus while it runs.

Parameters
defaultsWhat the chip should load at power-up; Validate() applies.
Returns
Ok, NotInitialized, InvalidArgument, Busy (a one-shot is pending), Bus, Timeout, BadReply, EepromVerifyFailed. After any error the driver is uninitialised.
